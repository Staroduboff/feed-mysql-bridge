# Нагрузочный тест WebSocket-раздачи витрины

Инструменты для ответа на вопрос «сколько одновременных клиентов держит раздача котировок».
Цель — Centrifugo витрины `sport-live` за nginx на тест-сервере *10 (`46.62.223.10`).

Нагрузку создают **протокольные клиенты**, а не браузеры: два headless-Chromium занимают
около 2.5 ГБ и полностью загружают четыре ядра, поэтому браузерами измеряется поведение
фронта (см. `../wsmon.js`), а ёмкость раздачи — этими скриптами.

## Состав

| файл | где запускается | назначение |
|---|---|---|
| `wsload.js` | машина-генератор | клиенты, ведущие себя как страницы витрины |
| `ladder.sh` | машина-генератор | лестница ступеней со сторожем |
| `wsguard.py` | машина-генератор | предохранитель: обрывает нагрузку, если она мешает хозяину сервера |
| `wsmetrics.py` | цель (*10) | метрики цели раз в 5 с в JSON Lines |
| `ladder_report.py` | цель (*10) | сводка по ступеням из файла метрик |

## Два измерения, которые нельзя смешивать

Нагрузка на раздачу — это не число соединений, а **fan-out = клиенты × поток на клиента**,
а поток на клиента задаёт ширина подписки. Поэтому измеряются отдельно:

- **Ёмкость по соединениям** — режим `narrow` (2 канала на клиента, как страница события):
  тысячи клиентов при десятках Мбит/с. Показывает пределы Centrifugo, nginx, файловых
  дескрипторов и портов.
- **Ёмкость по fan-out** — режим `wide` (каналы всех видов спорта плюс до `--events` каналов
  событий, как страница списка): ограниченное число клиентов, дальше пересчёт на клиента.
  Гнать до насыщения канала не нужно и нельзя, если генератор делит сеть с чужой работой.

Режим `mix` совмещает: доля `--narrow-share` клиентов работает как страница события.

## Как запускать

На цели:

```bash
python3 wsmetrics.py 1500 /tmp/wsload/target.jsonl     # секунд, файл
```

На генераторе:

```bash
bash ladder.sh narrow 200,500,1000,2000,4000 120       # режим, ступени, полка в секундах
bash ladder.sh wide   50,100,200,400 180 120           # + каналов событий на клиента
```

Разбор:

```bash
python3 ladder_report.py /tmp/wsload/target.jsonl
```

## Что меряется на клиентах

Принятые сообщения и байты, отказы подписки по кодам ошибок, обрывы, **пропуски в нумерации
`offset`** (потерянные публикации) и **разброс доставки одной публикации между клиентами** —
для выборки каналов запоминается, когда каждый клиент увидел публикацию с данным `offset`, и
считается задержка относительно первого получателя. Это прямая метрика деградации fan-out, и
она не требует правок в боевом коде моста.

## Что меряется на цели

Клиенты, подписки и каналы Centrifugo, отправленные им сообщения и байты, ошибки ответов,
соединения nginx, процессор, память и исходящий трафик сервера, а также **состояние моста** —
глубина очереди, отставание и гейт приёма ставок. Последнее обязательно: публикатор моста
шлёт батчи в Centrifugo синхронно в потоке разбора AMQP, и если раздача под нагрузкой начнёт
отвечать медленнее, замедлится разбор очереди фида.

## Предохранители

`wsguard.py` на генераторе каждые 5 секунд проверяет сеть, отклик mysqld (по приветственному
пакету на порт 3306 — учётная запись не нужна и на диске не хранится), load и свободную
память; при выходе за пороги шлёт генератору `SIGTERM`, тот корректно закрывает соединения и
печатает итог. Пороги в начале файла. В самом `wsload.js` есть `--max-rx-mbit`.

## Дробите генератор на процессы

JavaScript однопоточен: один процесс Node с тысячами сокетов упирается в ядро и начинает сам
добавлять задержку в то, что мы измеряем. Разница на одной и той же нагрузке 14.09.2026,
16 000 клиентов с узкой подпиской:

| | один процесс | восемь процессов по 2 000 |
|---|---|---|
| разброс доставки p50 / p95 | 277 / 574 мс | **58 / 124 мс** |
| CPU цели медиана / пик | 22.5 % / 93.9 % | **17.2 % / 48.2 %** |
| CPU процесса-генератора | у потолка | 5–6 % |

Правило: держать `cpuPct` каждого процесса ниже примерно 70 %; он печатается в каждой строке
статистики и в итоге прогона, а при превышении итог сопровождается предупреждением.

## Замер 14.09.2026: ёмкость по соединениям

Генератор — `mixdev` (`65.21.77.24`, 12 ядер, 62 ГБ, 0.4–2.2 мс до цели). Цель — 4 ядра,
7.6 ГБ. Узкая подписка (2 канала на клиента), дневной слейт: живых событий около пяти.

| клиентов | подписок | отказов | потерь | разброс доставки p50 / p95 | CPU цели медиана / пик | RAM цели | исход цели |
|---:|---:|---:|---:|---|---|---:|---:|
| 200 | 400 | 0 | 0 | 18 / 51 мс | 2.5 % / 25 % | 1.5 ГБ | 8 Мбит/с |
| 1 000 | 2 000 | 0 | 0 | 56 / 216 мс | 3.2 % / 15 % | 1.6 ГБ | 38 Мбит/с |
| 4 000 | 8 000 | 0 | 0 | 66 / 270 мс | 5.7 % / 18 % | 1.9 ГБ | 96 Мбит/с |
| 8 000 | 16 000 | 0 | 0 | 150 / 297 мс | 15.8 % / 46 % | 2.3 ГБ | 203 Мбит/с |
| **16 000** | **32 000** | **0** | **0** | **58 / 124 мс** | **17.2 % / 48 %** | **3.1 ГБ** | **183 Мбит/с** |

Строка 16 000 снята восемью процессами и потому единственная свободна от искажения генератора;
ступени до 8 000 гнались одним процессом, их задержки завышены (CPU цели в тех же ступенях
измерен корректно).

Мост нагрузки не заметил ни на одной ступени: очередь 94–286, отставание 0 с, гейт `OPEN` всё
время; RSS Centrifugo до 766 МБ, моста 132 МБ. На генераторе отклик mysqld держался 0.2–1.8 мс,
load не выше 4.6, пик входящего трафика 228 Мбит/с — дев-БД теста не почувствовала.

Потолок по соединениям при узкой подписке не достигнут: на 16 000 клиентов цель тратит
половину процессора в пике и 18 % гигабитного канала. Линейная экстраполяция по процессору
даёт порядка 30 000 клиентов, но проверять это надо отдельным прогоном, а не арифметикой.

**Что замер вскрыл помимо чисел.** Под нагрузкой публикатор моста восемь раз получил
таймаут на `POST /api/batch` и выбросил 6311 дельт: тогда одна просрочка выключала отправку
на `retry_s` = 5 с, и всё это время дельты уходили в мусор. Очередь фида при этом не росла —
терялась именно раздача в браузеры, то есть цены на экранах могли остаться неверными.
По итогам поведение публикатора переделано (одиночная неудача возвращает пачку в буфер,
отбрасывание — только после серии неудач), потери стали сигналом гейта приёма ставок и видны
на витрине здоровья. Подробности — в `../../../centrifugo/README.md`.

Повторный прогон тех же ступеней после правки (14.09.2026, 8 процессов):

| | до правки | после правки |
|---|---:|---:|
| потеряно дельт за прогон | 6 311 | **0** |
| 16 000 клиентов, CPU цели медиана / пик | 17.2 % / 48.2 % | 23.6 % / 45.5 % |
| 16 000 клиентов, разброс доставки p50 / p95 | 58 / 124 мс | 26 / 121 мс |

Плата за пятисекундный таймаут — короткое отставание разбора: очередь доходила до 907
сообщений, отставание мелькало 2 с вместо постоянного нуля. При скорости 565 msg/s это
полторы секунды очереди против порога гейта в 30 секунд.

**Что этот замер НЕ показывает.** Он снят днём, когда живых событий около пяти, и с узкой
подпиской. Нагрузка на раздачу определяется произведением «клиенты × ширина подписки», поэтому
вечером, когда живых событий три сотни и страница списка подписывается на сотни каналов, поток
на клиента будет в разы больше. Ёмкость по fan-out меряется отдельным прогоном в режиме `wide`
на вечернем слейте.

Прежде чем мерить, пришлось поднять два потолка, которые срабатывали раньше настоящей ёмкости:
`client.channel_limit` Centrifugo (было 128 при 8 + до 400 каналах у страницы) и
`worker_connections` nginx (было 768, а каждый проксируемый WebSocket занимает два соединения).
Подробности — в `../../../centrifugo/README.md`.
