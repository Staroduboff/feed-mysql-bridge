# centrifugo/ — раздача дельт кэфов по WebSocket

Слой реального времени над базой `feed_bridge`: клиент (страница спорта или
матча) берёт **снимок** кэфов из MySQL, а **изменения** получает по WebSocket
из Centrifugo, в который их публикует сам бридж. Выбор Centrifugo как
транспорта и HTTP-публикации батчами из бриджа — решение владельца от
07.09.2026; на тест-сервере *10 всё стоит рядом с бриджем, позже возможен
вынос на отдельный хост.

## Схема

```
betsportserver ──AMQP──▶ feed-mysql-bridge ──upsert──▶ MySQL feed_bridge  (снимок: REST, позже)
                              │
                              └─ после commit: буфер дельт ──POST /api/batch (каждые 200 мс
                                 или по 500 команд)──▶ Centrifugo 127.0.0.1:8000
                                                          │
                          браузер ◀── wss://gem.x1b.site/centrifugo/connection/websocket ── nginx
```

Публикация никогда не блокирует запись в базу: короткий таймаут, при сбое
пауза 5 с с отбрасыванием дельт (клиент восстанавливает пропуски через
recovery Centrifugo или перечитывает снимок). База всегда не старее WS:
дельты уходят только после commit.

## Каналы и формат сообщения

| Канал | Кто подписан | Что приходит |
|---|---|---|
| `sport:{sportId}` | страница/список вида спорта | дельты **событий** этого вида спорта (стадия, статус, счёт) |
| `event:{eventId}` | страница матча | дельты события, его **маркетов** и **исходов** |

Сообщение — запись `data` AMQP-потока фида без изменений (объект как в Redis,
см. `PARTNER_INTEGRATION_GUIDE.md` §3.3), завёрнутая в конверт:

```json
{"ch": "outcomes", "k": "o:18369749:c165ae1b…:[1,[],[0],1,3,[]]", "d": {"price": 4.98, "status": 1, "result": 0, "removed": false, "...": "..."}}
```

`ch` — канал фида (`events` / `markets` / `outcomes`), `k` — Redis-ключ объекта,
`d` — сам объект. Правила применения те же, что для снимка и AMQP: события по
`d.dv`, маркеты по `d.ver`, исходы — всегда. Для списка спорта клиент может
дополнительно подписаться на `event:{id}` видимых событий: подписок на одном
соединении может быть много, это штатно для Centrifugo.

Обе группы каналов доступны анонимно (кэфы публичны), с историей 300–500
публикаций на 60 с и `force_recovery` — короткий обрыв соединения клиент
переживает без перечитывания снимка.

### Завершение и удаление событий: контракт для клиента

Фид не присылает удалений: ключ события живёт в Redis, пока оно активно, и
ровно 24 часа после `status: 3`; маркеты и исходы удаляются вместе с ним. Из
этого следуют три правила для страницы:

1. **`status: 3` у события — терминальное состояние.** Дальше по событию
   приходят только расчёты исходов (`status: 4`, `result`), новых кэфов не будет.
2. **Убирать матч со страницы после расчёта исходов, но не позже чем через
   2 часа после `status: 3`.** Замер по 11 321 live-событию, завершённому за
   двое суток (07.09.2026): 99 % рассчитываются полностью, медиана задержки от
   завершения до последнего расчёта 6 с, p90 — 20 мин, p99 — 31 мин, максимум
   85 мин; 1 % событий (105) фид не рассчитывает вообще — у них все исходы
   остаются `status: 1`, и без таймаута страница держала бы их вечно.
3. **`{"ch":"events","k":"e:…","d":null}` — событие удалено из линии.** Такую
   дельту публикует сборщик `bridge.py --sweep`, когда ключ активного события
   пропал из Redis без завершения (аномалия фида, «зомби»); клиент убирает
   событие сразу. В штатном сценарии эта дельта не приходит: удаление через
   24 часа после `status: 3` клиенту не нужно, он уже убрал матч по правилу 2.

В базе всё это отражает сборщик: `removed=1` и `gone_at` для событий, ключи
которых истекли или пропали, каскадом на маркеты и исходы, и удаление строк
через 7 суток. Снимок (`snap/{id}.json`, позже REST) отдаёт только `removed=0`.

## Установка на сервере (Ubuntu, как на *10)

1. Пакет из релизов GitHub (на *10 стоит v6.9.4):
   ```
   curl -sSL -o /tmp/centrifugo.deb https://github.com/centrifugal/centrifugo/releases/download/v6.9.4/centrifugo_6.9.4-0_amd64.deb
   dpkg -i /tmp/centrifugo.deb          # ставит /usr/bin/centrifugo, systemd-юнит, /etc/centrifugo/config.json с ключами
   ```
2. Конфиг: за основу `centrifugo/config.example.json`, ключи `hmac_secret_key`,
   `http_api.key`, `admin.password/secret` взять из сгенерированного при
   установке `/etc/centrifugo/config.json` (или `centrifugo genconfig`).
   Проверка и запуск:
   ```
   centrifugo checkconfig -c /etc/centrifugo/config.json
   systemctl enable --now centrifugo
   curl -s -X POST -H "X-API-Key: <http_api.key>" http://127.0.0.1:8000/api/info -d '{}'
   ```
   Сервер слушает только `127.0.0.1:8000`: HTTP API, админка и `/metrics`
   снаружи недоступны.
3. nginx: сниппет `centrifugo/centrifugo.nginx.conf` в нужный `server`-блок
   (наружу только `/centrifugo/connection/`), `nginx -t && systemctl reload nginx`.
4. Бридж: в `config.json` секция
   ```json
   "centrifugo": {"enabled": true, "api_url": "http://127.0.0.1:8000/api", "api_key": "<http_api.key>", "batch_ms": 200, "batch_max": 500}
   ```
   и `systemctl restart feed-bridge` (режим `--listen`, база не чистится). В
   журнале появится строка `✓ Centrifugo: батчи по 200 мс / 500 команд`, а в
   строке статистики — счётчики `centrifugo: … опубл. в … батчах`.

## Проверка

- Демо-страница `centrifugo/ws-demo.html` (на *10 выложена как
  `https://gem.x1b.site/feed-health/ws-demo.html`): вид спорта и событие
  выбираются из выпадашек, слева сырой поток, справа расшифровка каждой дельты
  (что за событие/маркет/исход, кэф было → стало, смена статуса, счёт).
  Данные для выпадашек и расшифровки пишет сборщик витрины раз в минуту:
  `feed-health/catalog.json` (виды спорта, live и prematch-события на 12 ч,
  названия типов маркетов) и `feed-health/snap/{eventId}.json` (маркеты и
  исходы live и стартующих в ближайший час событий). Демо подгружает снимок
  при подписке на событие — ровно та схема «снимок из базы + дельты по WS»,
  по которой будет работать клиент; статические файлы здесь — прототип
  будущего REST-снимка.
- Метрики Centrifugo: `curl -s http://127.0.0.1:8000/metrics | grep centrifugo_node_`
  (клиенты, каналы, отправленные сообщения).
- Админка: `http://127.0.0.1:8000/` через SSH-туннель
  (`ssh -L 8000:127.0.0.1:8000 root@46.62.223.10`), пароль из конфига.
